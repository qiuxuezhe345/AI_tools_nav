## 三、项目简介

我最近在给一个 AI 导航站补后台管理系统。

这个站点本身已经有几张核心业务表：

- `ai_tools`：正式上线的 AI 工具数据
- `tool_categories`：工具分类
- `tool_submissions`：用户提交待审核的数据

但只有前台远远不够。  
一旦开始运营，就会遇到几个非常现实的问题：

- 管理员如何手动新增工具？
- 用户提交的工具如何审核？
- 审核通过后，怎么把提交数据同步到正式工具表？
- 非管理员如何禁止进入后台？
- 多个管理员之间如何管理权限？

所以这次我做的，不只是几个页面，而是一套完整的后台管理闭环。

---

## 四、项目目标

这个后台的核心目标很明确：

1. 只有管理员可以进入后台
2. 管理员可以查看平台概览数据
3. 管理员可以新增、编辑、查看、删除 AI 工具
4. 管理员可以审核用户提交的数据
5. 审核通过后，自动写入 `ai_tools`
6. 管理员可以管理其他管理员权限
7. 管理员可以管理工具分类

换句话说，这套系统解决的是一个 AI 内容站点从“能展示”到“能运营”的问题。

## 五、技术栈

这个项目主要使用了下面这些技术：

- `Next.js 15`
- `React 19`
- `TypeScript`
- `Supabase`
- `@supabase/supabase-js`

技术选型的思路也很直接：

- `Next.js` 负责后台页面、服务端渲染和 API Route

## 六、数据库设计

### 1. 正式工具表：`ai_tools`

这是站点真正展示给用户的数据来源。

字段里主要包括：

- 工具名称
- slug
- 官网地址
- logo
- 封面图
- 分类
- 简短描述
- Markdown 详情内容
- 是否热门
- 是否最新
- 发布状态

### 2. 用户提交表：`tool_submissions`

普通用户提交的数据不会直接进正式表，而是先进入这个表，状态默认是 `pending`。

它的意义很关键：

- 和线上正式数据隔离
- 方便管理员审核
- 可以记录审核结果和审核备注

### 3. 分类表：`tool_categories`

用于管理站点的工具分类，比如：

- AI 写作
- 图像生成
- 视频制作
- 语音处理

这个表支持：

- 分类名称
- slug
- icon
- 排序值
- 是否启用

### 4. 管理员表：`admin_users`

这是整个后台权限系统的核心。

我额外增加了一张 `admin_users` 表，用来标记谁有后台访问权限。  
只有在这张表里的用户，才算管理员。

这样做的好处是：

- 不影响普通用户注册登录逻辑
- 权限粒度清晰
- 后续要扩展 `super_admin` 也很方便

## 七、后台是怎么设计的

后台目前拆成了几个核心模块：

### 1. 概览页

概览页是管理员登录后的首页，负责提供全局状态和快捷入口。

目前展示了 4 个核心统计：

- AI 工具总数
- 分类总数
- 今日提交数
- 待审核数

同时在顶部导航里提供了几个独立模块入口：

- 概览
- 工具分类
- AI 工具管理
- 审核中心
- 用户管理

### 2. AI 工具管理

这是后台最核心的内容管理模块。

现在已经支持：

- 新增 AI 工具
- 查看工具详情
- 编辑工具
- 删除工具

在新增工具时，我还接了两个重要能力：

- Logo 上传到 Supabase Storage 的 `tool-logos`
- 封面图上传到 Supabase Storage 的 `tool-covers`

另外，`content` 字段支持 Markdown 编辑和预览，这样工具详情内容就不会只是一个普通文本框。

### 3. 审核中心

审核中心对接的是 `tool_submissions`。

它现在支持三个状态分类：

- 待审核
- 已通过
- 已驳回

管理员可以：

- 查看提交详情
- 点击通过
- 点击驳回

审核通过时，系统会做两件事：

1. 把当前提交的数据插入到 `ai_tools`
2. 把当前提交状态更新为 `approved`

同时还会写入：

- `approved_tool_id`
- `reviewed_at`

如果是驳回，则会把状态更新为 `rejected`，并记录审核备注。

### 4. 用户管理

用户管理页面用于控制“谁可以进入后台”。

这里的逻辑不是直接改 Supabase Auth，而是：

- 列出所有已注册用户
- 判断用户是否在 `admin_users`
- 支持设为管理员
- 支持取消管理员身份

我还额外加了一个保护：

- 不能删除最后一个管理员

这样可以避免后台彻底失控。

### 5. 工具分类管理

分类模块主要维护 `tool_categories`。

现在支持完整 CRUD：

- 新增分类
- 编辑分类
- 查看分类列表
- 删除分类

删除时我还加了安全校验：

- 如果分类已经被 `ai_tools` 或 `tool_submissions` 引用，就不允许删除

这样可以避免线上数据挂掉。

## 八、权限系统是怎么做的

这一块是整个项目里我最重视的部分之一。

因为后台权限不能只靠前端隐藏按钮，必须在服务端真正拦住。

我采用的是三层校验：

### 1. 登录后校验是否为管理员

用户即使账号密码正确，如果不在 `admin_users` 表里，也不能进入后台。

### 2. 中间件保护后台路由

对 `/protected` 和 `/admin` 路由做拦截。  
未登录或非管理员，直接跳回登录页。

### 3. 所有后台 API 再做一次管理员校验

也就是说，即使前端被绕过，后端接口依然会拒绝非管理员请求。

这个设计的意义很简单：

- 前端负责体验
- 服务端负责安全

---

## 九、为什么我没有在页面里直接查 Supabase

这个项目里我专门约束了一件事：

> 页面不直接操作 Supabase，所有数据库读写都走 API。

这样做有几个好处：

- 权限逻辑集中在 API 层
- 更方便统一使用 `service_role`
- 页面更干净，职责更清晰
- 后期更容易接日志、限流、审计

同时，后台的数据库操作统一通过服务端私钥客户端来做，也就是 `service_role` 模式。

这可以绕开前台 RLS 场景里很多不必要的限制，但前提是一定要把管理员校验写严。

## 十、这个项目里几个比较关键的实现点

### 1. 审核通过不是“改个状态”那么简单

审核通过本质上是一个“数据迁移”动作：

- 从 `tool_submissions`
- 到 `ai_tools`

所以它不能只更新一条状态，而是要先插入正式表，再回写审核表。  
这里如果处理不好，就容易出现脏数据。

### 2. Markdown 内容让后台录入体验好很多

很多工具并不只是一个标题和链接，实际上需要详细介绍：

- 工具做什么
- 适合谁用
- 优势是什么
- 场景有哪些

所以我在后台直接支持了 Markdown 编辑和预览，后面做内容运营会轻松很多。

### 3. Storage 上传是内容后台里非常实用的一步

如果图片地址全靠手填，很容易出错。  
接好上传之后，管理员只需要上传文件，系统自动返回可用 URL，体验会好很多。

### 4. 分类删除一定要做引用校验

这是后台系统里很容易被忽略的小细节。  
如果分类被删除，但工具还在引用它，前台展示、后台编辑、统计逻辑都会乱掉。

所以“能不能删”其实是后台稳定性的一部分。

## 十一、开发过程中踩过的几个坑

### 1. 环境变量命名不一致

一开始项目里用了旧变量名，但本地环境里是新变量名，导致登录注册直接报：

`Supabase environment variables required`

这个问题看起来像认证坏了，实际上只是变量名没有统一。

### 2. 编码问题会让页面看起来像“代码没问题，但文字全坏了”

在这次开发里，部分文件出现过中文乱码。  
这类问题最烦的地方在于：

- 代码能跑
- 类型能过
- 但文案和 JSX 看起来非常诡异

最后我的处理方式很直接：

- 对关键页面整文件重写成干净 UTF-8

### 3. 表格布局在后台非常容易翻车

尤其是分类列表这种：

- 列多
- 文本长
- 还有图片/图标

如果不做最小宽度和横向滚动，页面非常容易重叠。  
后来我给表格补了：

- `min-width`
- `overflow-x-auto`
- 特定列不换行
- URL/slug 自动断行

稳定性就好了很多。

### 4. 图片 URL 不等于图片一定能显示

即使数据库里有 URL，也不代表页面一定能加载成功。  
比如：

- bucket 不是 public
- 地址 403
- 地址格式不是标准 http/https

所以我后来给分类图标补了图片失败兜底逻辑，至少不会显示成空白。

## 十三、我对这个项目的总结

这次后台开发对我来说，最大的价值不只是“做了几个页面”，而是把一个 AI 导航站真正补成了可以运营的系统。

它已经形成了一个比较完整的闭环：

- 普通用户提交工具
- 管理员审核数据
- 审核通过后进入正式工具库
- 管理员可以继续编辑、分类、维护
- 权限系统保证后台只对管理员开放

从产品角度来看，这套后台把“内容增长”和“内容治理”同时解决了。  
从工程角度来看，这个项目也让我把 Next.js、Supabase、后台权限、审核流和 Storage 上传这些能力真正串起来了。

## 十四、可直接发布的简短版结尾

如果你也在做内容平台、导航站、工具站，后台管理系统其实是迟早都要补的一环。

相比一开始就追求很重的管理系统，我更推荐像这次这样：

- 先围绕真实业务表设计
- 先把权限、审核、内容管理闭环做好
- 再逐步增强搜索、筛选、日志和角色体系

这样系统不会过度设计，但也足够支撑真实运营。
